# Архитектура «Солнечного компаса»

Документ описывает, как устроено приложение версии 2.0.0, и объясняет решения,
которые из кода не очевидны. Для порта на Swift см. [SWIFT_PORT.md](SWIFT_PORT.md).

## Принципы

1. **Один файл, ноль зависимостей.** Всё приложение — `index.html`: встроенный SunCalc,
   стили и логика. Нет сборки, нет npm, нет транспиляции. Правка — открыть и отредактировать.
2. **Прибор, а не карта.** На экране нет меню, карт и настроек. Только кольцо, часы и кнопка спуска.
3. **Ничего наугад.** Каждая точка на диске имеет физический смысл.
4. **Сложность прячется, а не навязывается.** По умолчанию прибор отвечает на один вопрос —
   «когда солнце будет вон там». Ход солнца за сутки, зоны света и таблица времён спрятаны
   в инженерный режим, который надо найти.

## Секции `index.html`

Скрипт разбит на именованные секции; порядок в файле — снизу вверх по зависимостям.

| Секция | Ответственность |
|---|---|
| SunCalc 2.0.1 | Астрономия: `getPosition`, `getTimes`. Встроен без минификации |
| Версия приложения | `APP_VERSION` — единый источник правды, дублируется в `sw.js` |
| Безопасное хранилище | Обёртка над `localStorage` с фолбэком в память (приватный режим Safari) |
| DOM-элементы, деления, буквы | Генерация рисок компаса и N/E/S/W |
| Машина состояний | `IDLE → PERMISSION → READY ⇄ CALCULATING → LOCKED` |
| Компас | Сглаживание курса, вращение SVG |
| Одометр | Барабаны часов и хаотичный режим |
| Zoom-режим | Увеличение и смещение компаса под кнопку спуска |
| Астрономия | Азимут/высота, обратный поиск времени |
| Фазы освещения | `SUN_PHASES` — пороги высоты солнца |
| Инженерный режим | Переключатель, два режима радиуса |
| Траектория солнца | Выборка суток, градиентная отрисовка |
| Легенда зон | Таблица времён зон дня, выдвижная панель |
| Управление состояниями | Замер, сброс, ролик |
| Инициализация и разрешения | Онбординг, права, геолокация, геокодер |
| Service Worker | Регистрация офлайн-режима |

## Система координат кольца

Компас — вид сверху. SVG-холст 340×340, центр (170, 170).

```
экранный угол = азимут − 90°        (0° азимута смотрит вверх)
x = 170 + r · cos(угол)
y = 170 + r · sin(угол)
```

Весь `<svg>` вращается через CSS `transform: rotate(−visualHeading)`, поэтому траектория
и деления поворачиваются вместе как единый диск — так же, как в настоящем приборе.

### Инженерный режим

По умолчанию на диске нет ни траектории, ни зон: белая точка солнца на орбите `r = 115`,
золотая мишень замера на внешней `r = 140` — и всё. Это осознанное решение, а не экономия.
Прибор, который читается без объяснений, стоит дороже прибора, который показывает всё сразу.

Четыре тапа открывают инженерный режим — пасхалку. Состояние живёт в `localStorage`, признак
включения тихий: приписка `SN-01` у номера версии (по имени дизайн-концепта прибора).

Различает режимы только радиус, обе ветви — в одной функции:

```js
function altitudeToRadius(altitude) {          // солнце «сейчас» и летящая точка ролика
    if (!hiddenMode) return HORIZON_R;         // обычный: орбита 115
    const r = HORIZON_R * (1 - altitude / 90); // инженерный: радиус = зенитное расстояние
    return Math.max(PATH_MIN_R, Math.min(PATH_MAX_R, r));
}

function targetRadius(altitude) {              // мишень результата
    return hiddenMode ? altitudeToRadius(altitude) : TARGET_R;
}
```

Проекция инженерного режима:

| Высота | Радиус | Где на диске |
|---|---|---|
| +90° (зенит) | 0 | центр |
| +30° | 77 | между центром и горизонтом |
| 0° (горизонт) | 115 | ровно на пунктирной окружности |
| −6° | 123 | сразу за горизонтом |
| −18° | 138 | внешняя граница траектории |

Деления начинаются с радиуса 148, поэтому траектория никогда с ними не пересекается.
Глубже −18° дуга не рисуется: ночью показывать нечего.

Почему именно полярная проекция, а не дуга на кольце: ближе к экватору солнце проходит почти
через зенит, за весь день азимут меняется мало, и на кольце сутки сжались бы в короткий штрих,
а золотой час — в точку. Радиус по высоте разворачивает те же сутки на всю ширину диска.

Переключение режима на зафиксированном замере не сбрасывает результат: мишень пересаживается
на новый радиус по сохранённой `lockedAltitude`. Выборка суток строится только когда режим
включён — в обычном режиме `renderSunPath()` выходит на первой строке.

### Легенда зон

Вторая половина пасхалки. В инженерном режиме строка состояния получает класс `expandable`,
каретку и обработчик: тап выдвигает снизу таблицу зон дня. Тап по самой таблице её убирает —
отдельной кнопки закрытия у прибора нет.

Времена приходят из готовых событий SunCalc (`sunrise`, `goldenHourEnd`, `goldenHour`, `sunset`,
`dusk` плюс `sunrise` следующих суток для конца ночи), а не из порогов `SUN_PHASES`. Это
сознательное расхождение: у таблицы времён своя логика — золотой час считается от видимого
восхода (−0.833°), а раскраска дуги ведёт его от 0°. Разница — считаные минуты, зато таблица
совпадает с тем, что показывают любые другие солнечные календари.

Панель перерисовывается вместе с положением солнца, но только пока открыта.

## Отрисовка траектории

`buildSunPathSamples()` берёт сутки **от локальной полуночи до следующей локальной полуночи**
(через `setDate(+1)`, а не «+24 часа» — иначе в дни перевода часов сутки были бы неверной длины)
и семплирует положение солнца каждые 2 минуты: 721 точка. Шаг выбран так, чтобы соседние точки
отстояли примерно на 1 пиксель дуги.

`renderSunPath()` идёт по выборке и складывает точки в «прогоны». Новый прогон начинается, когда:

- суммарная разница RGB с цветом начала прогона превышает 12, или
- точка пересекает границу «прошлое / будущее».

Каждый прогон — один `<path>` со своим цветом, прозрачностью и толщиной. Последняя точка прогона
дублируется как первая точка следующего, поэтому стыков не видно. На типичных сутках получается
около 110 элементов, отрисовка занимает ~1 мс — пересчёт раз в минуту ничего не стоит.

Цвет, прозрачность и толщина интерполируются по таблице `PATH_COLOR_STOPS`. Толщина не постоянна:
день проходит тонкой нитью (2.2–2.4), а съёмочные часы у горизонта утолщаются до 4.6 — так
золотой час, закат и синий час читаются первыми. Прошедшая часть суток идёт на 45 % прозрачности
и 60 % толщины: видна, но не спорит с тем, что ещё впереди.

На диске сознательно нет ни засечек восхода и захода, ни часовых меток, ни подписей: любая
дополнительная метка ломает ритм делений и превращает прибор в диаграмму. Времена восхода
и захода живут в строке состояния, а полная разбивка суток — в выдвижной легенде.

## Обратная солнечная задача

Вопрос «когда солнце будет на азимуте A» — это обратная задача: обычные библиотеки считают
положение по времени, а нужно время по положению. `findSolarPassage()` решает её в два уровня:

1. **Грубое сканирование** — год вперёд с шагом в час. На каждом часе берутся азимуты на границах
   интервала. `unwrapAzimuth()` приводит их к одной ветви, чтобы переход 359° → 1° не выглядел
   скачком на 358° назад; без этого ломались утренние и полярные траектории.
2. **Бинарный поиск** — 20 итераций внутри найденного часа. Точность ~3 мс, что заведомо избыточно,
   но стоит порядка микросекунд.
3. **Проверка кандидата** — прохождение принимается, только если высота ≥ `SEARCH_MIN_ALTITUDE`
   (−6°) и азимут сошёлся с точностью 0.5°. Иначе сканирование продолжается — так замер
   на «уже стемнело» автоматически переезжает на следующий подходящий день.

Объекты `Date` (`d1`, `d2`, `dMid`) переиспользуются через `setTime()`: за полный проход
создавалось бы под двадцать тысяч временных объектов, и мобильный Safari заметно подтормаживал.

Худший случай — азимут, на который солнце не приходит никогда (строго север в средних широтах):
полный проход года завершается за ~10 мс и возвращает `null`.

## Одометр

Часы — не смена текста, а четыре независимые бесконечные ленты по 1000 цифр (`TOTAL_SECTIONS · 10`).
Позиция ленты хранится в `rotations[i]` в единицах `em`; показанная цифра — `rotations[i] % 10`.

- Барабан всегда крутится **вперёд**: если цифра меняется с 9 на 0, лента едет на +1, а не на −9.
- Длительность анимации растёт с числом шагов (`0.45 + шаги · 0.12` с), задержка каскадная
  (`0, 80, 160, 240` мс) — старшие разряды трогаются позже, как в механическом счётчике.
- Когда лента подходит к своему краю, она беззвучно перескакивает в середину при выключенной
  анимации — пользователь этого не видит.
- «Сломанный механизм»: если результата нет, каждый барабан получает свой `setInterval`
  со случайной скоростью. Останавливается только сбросом.

## Курс компаса

`handleOrientation()` берёт `webkitCompassHeading` (iOS, уже от истинного севера), иначе
`360 − alpha` с поправкой на `screen.orientation.angle`.

Проверка идёт **на тип числа, а не на истинность**: `heading || fallback` съедал ровный 0°,
то есть взгляд строго на север давал случайное значение из другой ветви.

`isHeadingStable()` считает разброс **циклически**, относительно первого замера в окне:

```js
d = ((value − base + 540) % 360) − 180
```

Наивный `max − min` по сырым значениям давал размах 359° при дрожании около севера
(359.8° и 0.2°), и замер на север уходил в вечную «Калибровку».

Визуальный курс догоняет реальный линейной интерполяцией с коэффициентом 0.15 и коррекцией
через границу 360° — компас не дёргается и не проворачивается на полный круг.

## Устойчивость к фону

Браузер замораживает `requestAnimationFrame` в скрытой вкладке. Раньше это означало: свернул
приложение во время замера — вернулся в вечное состояние `CALCULATING`, из которого нет выхода,
потому что `toggleLock()` в этом состоянии не делает ничего. Приложение приходилось перезагружать.

Теперь финал ролика вынесен в идемпотентный `finishStory()`, а рядом с `requestAnimationFrame`
ставится сторож `setTimeout` на `STORY_TOTAL_MS + 1500`. Кто добежит первым, тот и завершает замер.

Дополнительно на `visibilitychange` пересчитываются положение солнца, траектория и минуты часов:
фоновые таймеры тоже душатся, и без этого при возврате какое-то время висели старые данные.

## Офлайн

`sw.js` использует **network-first для документа** и cache-first для остальной статики.
Обратный порядок (cache-first для HTML) означал бы, что установленное PWA навсегда залипает
на той версии, которую скачало первой.

`CACHE_NAME` содержит номер версии: смена `APP_VERSION` автоматически выбрасывает старый кэш
в обработчике `activate`. Запросы к `photon.komoot.io` не перехватываются вовсе — название
города либо приходит живым, либо не приходит.

## Известные ограничения

- **Наклон не компенсируется.** Приложение считает, что телефон держат горизонтально.
  Компенсация требует `deviceorientation` вместе с акселерометром — задача для Swift-версии,
  где доступен `CMDeviceMotion` с готовой матрицей ориентации.
- **Часовой пояс.** Время выводится по поясу устройства, а расчёт идёт по заданным координатам.
  Совпадает, пока пользователь физически находится в точке замера. В демо-режиме (координаты
  Москвы при отказе в геолокации) время будет показано по местному поясу устройства.
- **Траектория только на сегодня.** Если результат замера приходится на другой день, золотая
  точка встаёт на правильный радиус, но нарисованная дуга остаётся сегодняшней.
- **Один тап по компасу = замер.** В zoom-режиме компас занимает почти весь экран, и случайное
  касание запускает замер или сброс.
